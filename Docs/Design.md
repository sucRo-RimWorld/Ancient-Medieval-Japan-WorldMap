# Ancient & Medieval Japan - WorldMap — Design

**Repository:** `sucRo-RimWorld/Ancient-Medieval-Japan-WorldMap`. This is the **single canonical owner** of the optional fixed Japan archipelago Worldbuilder map preset and its future production release. The original Project [JapanWorldMapCandidate research](https://github.com/sucRo-RimWorld/Ancient-Medieval-Japan-Project/blob/main/Docs/Research/JapanWorldMapCandidate.md) is prior research/evidence and superseded prototypes, **not another active implementation owner**.

**Author's latest execution decision (2026-10-18): WorldMap execution priority is LOW, with unresolved work retained as ACTIVE backlog.** The optional Japanese world has strong potential value but comparatively poor near-term benefit for regular RimWorld play, which mostly takes place on a single settlement map. Reassess if practical direct world-map/map-to-map travel becomes a relevant playable feature, but do not presume any Exodus-style capability exists, make it a new dependency, or initiate travel-Mod development as part of WorldMap. Do not spend current implementation/test capacity on speculative world expansions while higher-impact Environment, Culture, Grains and other settlement-scale projects remain active. Existing source-only faction-base count reduction PR #9, intermediate-temperate biome ownership, Kyushu/neighbor-relief problem and remaining author-facing map acceptance requirements are all open, not cancelled or release-approved. Priority LOW does not mean geography is accepted, the source-only PR #9 DLL is rebuilt, or the previously released 1.6 package is updated. Subalpine/Alpine distribution retuning waits for WorldMap's own intermediate-temperate biome.

**Prior 2026-10-17 author condition remains a completion gate, not an immediate execution order: WorldMap development cannot be considered DONE until all four observed issues are corrected: ocean faction bases; too few subalpine and alpine regions; practical ordinary highland settlement sites; Fuji/Tateyama/Hakusan and similar approved sacred summits individually protected as impassable Alpine.** The earlier 'pause now while Environment forests mature' direction is superseded. Keep the accepted Japanese shape. Implement limited highland source improvement **without waiting for all wetland/forest-food content to finish**, coordinate new biome names with Environment, and perform one final native 1.6 playable review before pausing. 1.7, optional scenery, new features and public Workshop upload do not become automatic release targets.

## Purpose and user-visible target

An **optional**, fixed ancient-to-medieval Japanese world for RimWorld 1.6/target 1.7, built as a Worldbuilder saved preset. It is not a replacement for Environment's procedural/random planet. Target the Japanese islands supported by the original polygon selection (Honshu, Shikoku, Kyushu and ten other selected island polygons), **without Hokkaido or Ryukyu/Okinawa**, and preserve geography-specific climate and biomes rather than using the virtual globe's fantasy latitude as evidence of real Japanese vegetation.

The current 1.6 prototype has 590,492 planet tiles, 50,810 land-labelled tiles and 13 island components. A **recognized shape** is already demonstrable, but this is **not** an accepted final grid size, historical coastline, reliable ecological distribution or recommended normal public release. The **revised, native-accepted 1.6 XML pair and runtime DLL** from source `d3783c6779525d75e1f750bc3e874492190fca1e` are bundled under Mod-root `Worldbuilder/` and `Assemblies/`. The current XML source/destination Git Blob SHAs were checked against Project manual [Actions #39042174500](https://github.com/sucRo-RimWorld/Ancient-Medieval-Japan-Project/actions/runs/39042174500), and the runtime DLL comes from that same accepted build. The previous original author-approved **coastline shape** package remains archived at Actions #39022443969; the new regional mountain distribution is not yet author visually approved. Data provenance and distinct third-party attribution: [Docs/DataProvenance.md](DataProvenance.md).

Never claim medieval observations or exact forest composition.

## 2026-10-17 author's original 1.6 in-game review and follow-up

**Actually inspected by author:** 13-island Japanese **overall coastline/silhouette accepted (shape OK)**. Preserve existing approved island mask and original geographical layout. The user reported that **some generated nonplayer faction settlements are displayed on sea**; this is a demonstrated gameplay defect, not a potential future nice-to-have. They reported **too few subalpine/alpine cells** and that alpine-looking sites were overwhelmingly uninhabitable. New objective: **more settleable high-country and some genuinely inhabitable subalpine/alpine colony-map sites**, but **Fuji and other established sacred summit tiles must be impassable Alpine**, while surrounding slopes/foothills remain available for settlement.

### Offshore faction location (revised native 1.6 acceptance PASS)

Worldbuilder 1.6 calls its terrain restoration **after** Vanilla generation, in `World_FinalizeInit_Patch.RestoreWorld`; original Worldbuilder's `saveBases=false` route does not replace randomly placed faction bases. When the map becomes Japan-only, those old bases may remain at newly ocean-designated locations. WorldMap's **current source and rebuilt bundled DLL** extend its existing `RestoreTerrain` Harmony patch with a **postfix** that: identifies nonplayer `Settlement` objects on ocean/impassable cells; selects unused, original-engine-approved settlement positions on the restored actual Japanese land; moves the **existing** settlement instances (maintain faction/name/load-ID) through world object remove/add indexing; and verifies no invalid nonplayer settlement remains. It runs only for the exact `AMJ_Japan_World_Prototype` preset during fresh-world restore, never for arbitrary Worldbuilder presets, ordinary procedural Environment worlds or load-time reinitialization. **No existing user save is retroactively altered.** The revised preset 1.6 native acceptance in Actions #39042174500 observed **zero** nonplayer settlements on ocean/impassable terrain after restoration; this result does not prove any earlier save has been repaired.

### Mountain hilliness vs. alpine biome are different axes

- Original source incorrectly made **every tile over 2,400 m `Hilliness.Impassable`**, irrespective of sacred status; `AMJ_AlpineZone` is instead an actual loaded Environment **BiomeDef with nonzero `settlementSelectionWeight`**. One need not forbid settlements across an entire climate vegetation zone.
- **Source change:** non-sacred high-altitude tiles `>1500 m` have `Hilliness.Mountainous` rather than indiscriminate `Impassable`. Normal engine `TileFinder.IsValidTileForNewSettlement` and WorldMap terrain conditions still govern final settlement. This makes existing **non-sacred alpine** tiles candidates where the base game's rules permit, not proof of all-alpine colony viability.
- **Sacred summit exceptions:** the three traditionally designated sacred mountain peaks—**富士山 / Mt Fuji, 立山（雄山） / Mt Tateyama (Oyama), 白山（御前峰） / Mt Hakusan (Gozengamine)**—each map to **one closest real GIS-positioned Japanese land cell** (with a bounded 0.18-degree geographic proximity gate); the selected summit cell gets `AMJ_AlpineZone` and `Hilliness.Impassable`. Surrounding hills/valleys do not inherit this ban. This is a **specific symbolic summit placement overlay**, not a false claim that the sampled z8 DEM/modern climate measured the peak at 3,776 m or a historical snowline. **Do not assign other sacred mountain identities or sacrifice historically populated temple slopes by a broad mountain-wide lock.**
- **Active correction:** increase mountain evidence resolution, **not arbitrarily inflate alpine percentages**. Old 1.6 prototype used coarse GSI Global Map **DEMGM z8**; 1,268/50,810 subalpine (2.5%) and 33/50,810 Alpine (0.1%) were the *old output*, not accepted final targets. **New producer source now uses GSI Fundamental Geospatial Data DEM10B `dem_png` at z9**, with each relevant original Japan native-grid land centre sampled at geographic coordinates; still no arbitrary extrapolated mountain altitude. z9 is roughly twice the pixel resolution per axis of z8 and uses better observed input. Verified source availability and encoding: [GSI elevation data](https://maps.gsi.go.jp/development/index.html) and [elevation PNG specification](https://maps.gsi.go.jp/development/demtile.html). Native owner [Actions #39039601606](https://github.com/sucRo-RimWorld/Ancient-Medieval-Japan-Project/actions/runs/39039601606) **FAILED** at the *acceptance-only C# compilation* (CS1061: `WorldObjectsHolder.worldObjects` is not an exposed 1.6 member); the export step itself produced an inspectable **unaccepted** candidate with *Subalpine 1,214 (down from 1,268)* and *Alpine 37 (up from 33)*. **DEM10B resolution alone demonstrably does not correct mountain scarcity.** Comparison of the WorldMap's old Kira cutoffs (subalpine 15≤WI<45; Alpine WI<15) with [Environment's canonical 2026 approved annual-temperature biome specification](https://github.com/sucRo-RimWorld/Ancient-Medieval-Japan-Environment/blob/main/Docs/Design.md) shows a direct inter-Mod mismatch: **Environment Subalpine annual 0–<8°C, Alpine <0°C**, warm/cool above 8°C. Accordingly, the current WorldMap producer uses that *already approved* annual-temperature boundary for **highland only**, retains the existing WI≥85 / CI≥−10 warm-forest eligibility above 8°C and else cool. This is correction to an established owner contract, **not a numerical biome quota** or arbitrary temperature change. Python uses the same rounded 0.001°C annual value read and validated by the Worldbuilder C# producer. Acceptance-only C# switches to Worldbuilder's existing proven `Utils.GetSurfaceWorldObjects<Settlement>()`. The first native run remains a recorded **FAIL** (acceptance C# compiler), not a PASS. The later, separate manual [Actions #39042174500](https://github.com/sucRo-RimWorld/Ancient-Medieval-Japan-Project/actions/runs/39042174500) **PASS** built and tested the revised `d3783c6` source and produced the new actual shipped XML/DLL. Its native assertions include zero invalid nonplayer settlement positions, non-sacred settleable subalpine/alpine terrain, exactly three impassable Alpine summit cells, the unchanged 50,810 land-cell silhouette, new colony, saving, and an independent 1.6 reload with Unity ERROR 0. Keep bounded GSI downloads, hash provenance and unresolved DEM labels. If the aligned mountain placement remains visibly deficient after acceptance, continue evidenced regional refinement before pausing.
- **Completed native acceptance (Actions #39042174500):** all surviving nonplayer settlements nonocean/passable; both mountain biome counts exceed DEMGM z8 1,268/33 baselines **without forcing biome proportions**; at least one settlement-capable subalpine/alpine tile; exactly three Alpine/Impassable summit cells; unchanged 50,810-cell original silhouette; full new-game/save/reload success. This is a minimum technical improvement gate, **not** proof that 55 Alpine tiles reflect an accepted or historically correct mountain distribution.

## 2026-10-18 author decision — WorldMap owns intermediate-temperate forest

**Confirmed ownership, not yet a shipped biome:** For the **optional fixed Japan Worldbuilder preset**, WorldMap is responsible for defining the additional **intermediate-temperate forest (中温帯林 / 中間温帯林)** as its own uniquely named `BiomeDef`, its WorldMap-specific vegetation and terrain composition, and its regional generation/placement. WorldMap can also own other explicitly Japan-geographic north/south or Japan Sea/Pacific-facing forest subdivisions where the fixed map needs them. The historical/environmental rationale and precise Def names, wildPlants values, weather/disease/animals behavior, and tile boundaries require later scoped design and audit before creating runtime XML.

**Environment remains the common ecological asset provider**: existing four general-purpose AMJ forest/alpine BiomeDefs and ordinary procedural worldgen, weather/climate infrastructure, and shared Japanese PlantDefs and their textures/harvest/foraging behavior remain Environment-owned. WorldMap does not fork tree/plant ThingDefs and must reference real installed Environment Defs, declaring Environment as the existing required dependency. A WorldMap-only intermediate BiomeDef must not be added to Environment or made globally naturally generated. Do not change Environment's established forest-climate thresholds or default random worlds to accommodate this optional specialization.

**Sequence:** implement and review the intermediate-temperate WorldMap biome and any necessary genuine shared plants first. **Only afterward** revise the fixed Japan distribution of Cool/Subalpine/Alpine and other north/south forest types; a 10°C/2°C temperature-threshold experiment was an unapproved discussion, not an adopted balance value. The independently identified terrain `Hilliness`/DEM neighbor-relief issue and excessive faction-base density can be addressed separately from this distribution sequence. The author-approved coastline remains untouched. No 1.7, Workshop or native PASS follows from a design decision.

## 2026-10-20 季節・農耕暦とWorldMapの実地理緯度 — 未解決の重要な連携課題

**発見と限定:** 作者はAMJの季節・農耕暦の検討時にWorldMapとの連携も考慮すると表明。現在のWorldMap本番生成ソース `Tools/Research/ProjectJapanCoastlineToTiles.py` の既定の座標変換は、**GIS北緯36° → RimWorld仮想緯度0°、仮想緯度倍率13倍** (`gis_lat=36.0, virtual_lat=0.0, latitude_scale=13.0`) である。`Tools/Production/build_japan_world_preset16.py` はこの投影ツールを追加の緯度上書きなしで呼び出す。これは地形を認識できる大きさへ引き延ばすための仮想球体座標で、**本来の日本の実緯度ではない**。概算例: GIS北緯32°→ゲーム南緯52°、GIS北緯35°→ゲーム南緯13°、GIS北緯36°→ゲーム赤道、GIS北緯41°→ゲーム北緯65°。地理的な形状を保持しているだけで「日本の春夏秋冬や日照も再現済み」という意味ではない。

**既存RimWorldとの干渉:** 通常のRimWorldは地図タイルの `WorldGrid.LongLatOf` で得る緯度から `GenDate.Season` / `SeasonUtility` 等の季節表示、日照時間、季節気温差を計算する。南半球では季節の位相が逆転する。WorldMapでは日本列島の南半分に仮想負緯度があるため、**季節位相・日照・屋外気温の年内推移が、日本の実地理とずれる強い構造的リスク**がある。WorldMapによるJMA月別気温を利用したGISベースの**年平均** `tile.temperature` 設定は、この仮想緯度ベースの年内変動や光周期の整合性を自動で証明しない。

- **優先する確認:** 対象Worldbuilder presetが選択されたときに限り、南側・中央・北側の代表タイルについて、実GIS緯度、ゲーム仮想緯度、季節名、月相当の最高/最低気温、日照時間、作物の生育可能期間を一体で検証する。現行の1.6新世界/セーブ再ロードPASSはこの季節整合性を検証しておらず、季節補正PASSとは呼ばない。
- **境界と設計の保留:** 修正の具体的技術（実GIS緯度の保存・提供、WorldMap-onlyのSeason/日照/気温補正、固定地図を北半球に配置し直す案など）は**未選択**。単純に `GenDate` を全ワールドへグローバルパッチしたり、Environmentのランダム地形・気温モデル、Grainsの作物 `growDays`、CCTOの休眠/枯死閾値を書き換えない。座標の持ち方が変わるとワールド形状・既存セーブにも影響し得るので、それを先に検討する。
- **他Mod連携:** 将来の祭礼・芸能子Modが「収穫期」「春の行事」などを扱う際、WorldMap利用時に実地理に整合した局所季節を参照できる方法を**検討**する。WorldMap非導入時はRimWorld標準の季節・気温・生育イベントで動く構成を維持する。農耕暦そのものをGrainsに強制しない。祭礼子ModやGrainsがWorldMap必須となることを意味しない。
- **既存の優先度を維持:** これは作者指摘に基づく既存WorldMapの季節整合性の監査課題であり、即時の大規模改修、追加nativeテスト、1.7互換、公開を承認しない。WorldMapの既存残作業・低い実行優先度と、Environment/Grains/Cultureの現行作業を尊重する。

**根拠:** [WorldMap投影ソース](../Tools/Research/ProjectJapanCoastlineToTiles.py)、[WorldMap地形出力](../Tools/Production/JapanWorldPresetBuilder16.cs)、[RimWorld `GenDate.Season` Decompile](https://github.com/josh-m/RW-Decompile/blob/master/RimWorld/GenDate.cs)、[RimWorld季節と緯度](https://rimworldwiki.com/wiki/World_generation)。**判定の状態:** 投影式はソースで確定、影響はRimWorldの通常の緯度依存モデルからの論理的帰結。**現行WorldMap本番DLLについて季節別のNative実測は未実施**。

## Ownership boundary, backlog and stop

1. **Environment** owns the existing four general-purpose climate/biome identities, shared species/PlantDefs, scenery resources and wild-food integration, including ordinary random-world ecology. **WorldMap** owns additional **Japan-fixed-preset-only BiomeDefs**, including the intermediate-temperate forest and possible geographic regional variants, their biome-local plant weighting and tile assignment. Distinct WorldMap biome identity is authorized; duplicating or redefining Environment's existing BiomeDefs/ThingDefs is not.
2. **WorldMap** also owns its preset resolution, coastline/river/elevation representation, geo-position mapping, WorldMap-only biome definitions/placement, Worldbuilder compatibility and optional packaged map.
3. Grains/Rice/Wild Food supply balance is evaluated in full AMJ separately; the presence of natural foods does not require WorldMap to implement food production or PlantDefs.
4. **Do not pause WorldMap yet.** The source-matched revised XML/DLL and one manual 1.6 native producer/acceptance have passed all four minimum technical gates. **The author's practical revised mountain-map review is still open**, particularly sparse Alpine 55 cells (~0.11%). If visibly deficient, refine geographic source/evidence rather than manipulate percentages and run only a focused end-stage retest. Keep WorldMap ACTIVE until the author's originally reported map problems are accepted; intermediate-temperate biome implementation precedes further geographic highland redistribution, and is not contingent on changing Environment's ordinary-world biome set. Forest-food Jobs, all wetland art, 1.7 and public release are not blockers for the four existing WorldMap defects.
5. **No Steam/public release** until original GIS/DEM terms and attribution, Mod package identity, true Worldbuilder selection, available platform profiles, geographic/ecological limits, privacy/publication gates and acceptance are satisfied.
